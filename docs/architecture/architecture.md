# 架构合同

> 本文拥有 Vibe-Finance 的判断权边界、存储分层与权威划分、知识事务与并发模型、运行形态和组件职责切分。对象目录的具体文件与内容合同以 [`../knowledge-design/wiki.md`](../knowledge-design/wiki.md) 为准；研究状态、复核节奏和报告的产品语义以 [`../research-design/research_design.md`](../research-design/research_design.md) 为准；SQLite 具体内容以 [`../data-design/data_design.md`](../data-design/data_design.md) §7 为准；运行时复用边界以 [`../../README.md`](../../README.md) Capability boundaries 为准。

## 1. Responsibility

本文负责：

- 确定 Agent 可以做判断的范围，以及约束它的结构性手段；
- 划分证据、知识、判断和投影四层的权威归属与越界规则；
- 定义知识写入的事务边界、校验项和并发模型；
- 确定周节拍复核的运行形态；
- 切分 Agent、确定性 Command、知识仓库、SQLite 和数据工具的职责。

本文不负责：

- 对象目录中每个文件的内容合同与格式；
- 用户可见的页面结构、状态语义和文案；
- 具体表结构、migration、接口形状和实现排期。

## 2. 判断权边界

本产品对外承诺的核心输出是研究状态、价值区间、估值位置和安全边际。这些都是判断，不是资料整理结果。因此系统必须允许 LLM 做判断，而不能停留在「只编译事实、判断全部交给人」的模式——那种模式适合研究综述和读书笔记，不适合一个要替用户回答「当前估值是否合理」的产品。

允许 LLM 判断的代价是它天然的顺从性：它倾向于配合上下文里的隐含倾向，而不是挑战它。约束手段不能是提示词，必须是结构性的：

| 约束 | 落地方式 |
|---|---|
| 来源分级 | FCISU 五级标注，用户陈述在获得外部证据前只是假设 |
| 证据不可销毁 | Raw 只追加，用户显式删除是唯一例外且必须留恢复路径 |
| 冲突不可静默解决 | 保留双方、标记存疑、形成知识缺口，不单边覆盖 |
| 机械工作归代码 | 落盘、日志、投影、提交、估值重算全部由确定性 Command 执行 |

**机械归代码、判断归 LLM、裁决归人**是本架构的第一原则。凡是可以由确定性代码可靠完成的事，不交给 Agent；凡是需要综合与取舍的事，Agent 可以做但必须援引证据；凡是破坏性或改变研究范围的事，由用户确认。

## 3. 四层存储与权威

```text
raw/sources/    证据层   摄取与用户写入   只追加        原始资料的唯一权威
wiki/           知识层   Agent 维护       累积式重写    事实与关系的唯一权威
judgment/       判断层   复核写入         会被推翻      研究状态、价值区间与论证的唯一权威
SQLite          投影层   Command 写入     可丢弃重建    不承担任何权威
```

分层的依据是可变性和失效方式不同，不是为了对称。证据不会失效，只会被替代；事实会被更精确的事实修正；判断会被推翻，因此需要保留变更历史；投影只是为了让列表页不必解析文件。

三条越界规则：

1. **Wiki 页面不得写入研究状态、价值区间或估值结论。** 判断只能出现在判断层。Wiki 只承载事实与关系，允许出现明确标注为 Inference 的推导，但不得出现对象级结论。
2. **判断层复述 Wiki 事实时必须带脚注锚点指回。** 判断层不是事实的第二权威；报告里的数字滞后于 Wiki 是允许的，由「待复核」表达，但不允许两处各自声称正确。
3. **SQLite 不得成为任何事实或判断的唯一存放处。** 删除整个数据库后，重新扫描知识仓库必须能完全重建。

判断层的内容合同、`verdict.md` 与 `report.md` 的分工、脚注锚点格式见 [`../knowledge-design/wiki.md`](../knowledge-design/wiki.md)。

## 4. 知识事务

所有对知识仓库的写入都经过同一条路径，分成两个性质完全不同的阶段。

**生成阶段（Agent）** 读取当前页面、分析资料、产出一个**变更集**：目标文件及其新内容、`log.md` 追加条目、报告状态标记。这个阶段慢、非确定、允许失败，全程不接触工作区。

**落盘阶段（Command）** 取对象锁 → 校验变更集 → 写文件 → 追加 Log → 更新投影 → 单次 Git commit → 释放锁。这个阶段快且确定，不调用模型。

校验至少拒绝以下变更集：

- 越层写入，例如 Wiki 页面中出现研究状态或价值区间；
- 关键数字缺少脚注锚点、FCISU 或 `data_as_of`；
- 冲突记录被单边删除；
- Raw 被原地改写；
- 轻复核的变更集触及待复核标记与 Log 之外的任何内容。

校验不通过或任一步失败时，**整个变更集丢弃**，工作区从未被修改，因此不存在 Raw 已改而 Wiki 未改、或报告写了一半的状态。这是 [`../knowledge-design/wiki.md`](../knowledge-design/wiki.md) 中「不能完整落盘、写日志并形成 checkpoint 时视为整体失败」的实现路径。

## 5. 并发

**锁按对象加。** 同一对象的知识事务串行，不同对象可以并行分析与复核。仓库级只在 commit 那一瞬间串行，而 commit 是毫秒级操作，不构成瓶颈。

不引入乐观并发控制、影子目录或工作分支。单用户桌面应用不存在需要这些机制的竞争强度，加了就是没有当前需求的预设计。

## 6. 运行形态

**周节拍轻复核是前台行为。** 系统只在应用运行时工作。

- **启动时**：检查每个关注对象距上次轻复核的间隔，超过一周的排队补做一次；无论关闭了多久都只补一次，不回放历史节拍；
- **运行中**：按各对象自己的计时到期触发，不设全局统一时点，因此不会出现集中复核；
- **关闭期间**：不工作；「最近更新」如实显示上次检查时间，不暗示期间仍在运行。

不建立常驻后台进程，不注册开机自启，不使用系统级定时器。这条决定了对外表述必须与之一致：不能宣称系统在用户不使用时仍持续盯盘。

## 7. 组件职责

| 组件 | 负责 | 不做 |
|---|---|---|
| Pi AgentSession | 阅读、分析、页面维护、解释、产出变更集 | 不直接写文件、不计算估值、不更新投影 |
| 确定性 Command | 校验、落盘、追加日志、更新投影、提交、恢复、估值与状态计算 | 不做判断、不生成叙述内容 |
| 知识仓库（文件 + 本地 Git） | 证据、知识、判断三层的权威存储与恢复 | 不存 tick、接口缓存、聊天历史 |
| SQLite | 列表查询、事件、数据源与上传索引的投影 | 不承担权威，不保存判断原文 |
| Vibe-Research 数据工具 | 行情、财务、估值、公告、行业数据获取 | 不写入知识仓库 |
| 前台调度 | 周节拍到期检查、披露窗口检查、任务重试 | 不驻留后台，不做系统级定时 |

Agent 与 Command 之间只有变更集一条通路。Agent 不得绕过 Command 写最终状态，Command 不得在没有变更集的情况下自行编造内容。

## 8. Failure semantics

| Failure | 行为 | 保留状态 |
|---|---|---|
| Agent 生成中断或超时 | 变更集未形成，工作区未改动 | 上一个 checkpoint |
| 变更集校验不通过 | 整体拒绝并记录拒绝原因，可重试 | 上一个 checkpoint |
| 写盘或 commit 失败 | 整次知识变更回滚 | 上一个 checkpoint |
| 对象锁等待超时 | 本次任务改期，不强制抢锁 | 上一个 checkpoint |
| 投影重建失败 | 列表页降级显示，知识仓库不受影响 | 全部知识资产 |
| 启动补做复核部分失败 | 失败对象保留原状态并可单独重试 | 其余对象正常完成 |

## 9. Business validation

- 删除 SQLite 后重新扫描知识仓库，关注列表、状态灯和更新时间可以完全重建；
- Wiki 页面中不出现研究状态、价值区间或估值结论；
- 判断层中的每个关键数字都能通过脚注锚点回到 Wiki 或 Raw；
- 任何一次失败的知识写入都不留下半成品，工作区始终等于最后一个 checkpoint；
- 轻复核的变更集无法通过校验去改写报告或研究状态；
- 多个对象可以同时复核，同一对象的两次写入不会互相覆盖；
- 应用关闭两周后重新打开，每个超期对象只补做一次轻复核，且「最近更新」显示真实的上次检查时间；
- 普通用户界面不出现变更集、锁、commit、hash 或文件路径。
