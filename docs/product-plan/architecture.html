架构实施说明

系统如何划分职责、存储与写入路径

研究状态、价值区间和估值位置都是判断。能按规则完成的事归执行器，判断归 Agent，会改范围或删东西的操作须用户确认；系统只在应用打开时运行。

系统总览

系统怎么拼在一起

前台调度触发任务；Agent 只提出要改什么；执行器是唯一真正写入的入口；数据工具只取数，不改知识档案。

系统架构 · 组件与数据流 运行结构
唯一通路：Agent → 变更方案 → 执行器 → 知识档案 / 列表索引。Agent 不直接改文件；数据工具不改知识档案。

确定性 → 执行器

写入文件、记日志、更新列表、保存变更点、重算估值：全部由执行器完成。

判断 → Agent

综合、取舍、页面维护、解释：Agent 可以做，但必须援引证据。

确认 → 用户

破坏性操作、改变研究范围、采用持续假设：用户确认后才生效。

分层存放

四层存放，每一层只认一个来源

分层依据是各自怎么变、怎么失效：证据会被替代，事实会被修正，判断会被推翻，列表索引随时可重建。

存储分层 · 谁写入、以谁为准 四层结构
1
Wiki 不得写入研究状态、价值区间或估值结论

判断只能出现在判断层。Wiki 可含明确标注为「推断」的推导，不得写价值区间或估值结论。

2
判断层复述 Wiki 事实时必须带脚注锚点指回

报告数字滞后于 Wiki 是允许的，用「待复核」表达；不允许两处各自声称正确。

3
列表数据库不得成为任何事实或判断的唯一存放处

删掉列表数据库后，重新扫描知识档案必须能完全重建。

知识写入

先提出变更方案，再过校验，再一次性写入

Agent 不能直接改档案文件。校验不过或任一步失败，这次变更全部作废。

知识写入 · 两阶段 + 校验 写入流程
结果保证：档案始终等于上一可恢复点。不会出现资料已改但 Wiki 未改，或报告只写了一半。
校验

校验门至少拒绝这些

固定规则拦住，不靠 Agent 自觉
01
越层写入

Wiki 出现研究状态或价值区间

02
关键数字缺标注

缺少脚注、来源分级或数据截至日

03
冲突被单边删除

抹掉对立来源而不留缺口

04
Raw 原地改写

覆盖已有资料内容

05
轻复核越权

触及「待复核」与 Log 之外的任何内容

轻复核红线：只能写判断状态里的「待复核」，以及认知日志。

同时写入与运行方式

同一对象排队写入；周节拍只在应用打开时工作

单用户桌面应用。不在后台偷偷跑，不开机自启，不用系统定时任务。

同时写入时怎么排队 排队
周节拍时间线 仅前台

组件职责

Agent 与执行器之间只有变更方案一条路

Agent 不能绕过执行器直接改最终状态；执行器不能在没有变更方案时自己编内容。

职责分工 · 谁做什么 / 不做什么 职责

失败语义

失败默认回到上一可恢复点

列表索引失败不影响知识档案；知识写入失败不留下写到一半的内容。

失败路径 · 全部回到上一可恢复点 失败
×

启动补做部分失败

失败对象保留原状态，可单独重试；其余对象正常完成。

×

界面保持业务语言

用户只看到变更记录与恢复，看不到排队、版本号或文件路径。

验收

完成后用这些条件检查

对象目录的文件内容见 Wiki 实施说明；这里验收系统骨架。

删除列表数据库后重新扫描知识档案，关注列表、状态灯和更新时间可以完全重建
Wiki 页面中不出现研究状态、价值区间或估值结论
判断层中的每个关键数字都能通过脚注锚点回到 Wiki 或 Raw
任何一次失败的知识写入都不留下写到一半的内容，档案始终等于上一可恢复点
轻复核提出的变更无法通过校验去改写报告或研究状态
多个对象可以同时复核，同一对象的两次写入不会互相覆盖
应用关闭两周后重新打开，每个超期对象只补做一次轻复核，「最近更新」显示真实的上次检查时间
普通用户界面不出现变更方案、排队、版本号或文件路径等内部细节
